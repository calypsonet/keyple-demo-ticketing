# Keyple Reload Demo

[![License](https://img.shields.io/badge/license-BSD_3_Clause-blue.svg)](../../LICENSE)

Client/server demonstration of the
[Eclipse Keyple Distributed Solution](https://keyple.org/docs/developer-guide/distributed-application/), where all the
ticketing procedures and sessions are managed by the server, the clients only giving access to the card.

[⬅️ Back to Main Project](../../README.md)

The server, using the [Eclipse Keyple](https://keyple.org) SDK and a SAM, personalizes the cards and loads the contracts
(Season pass and/or Multi-trip ticket) on Calypso cards and on storage cards. Several clients are provided:
- **Android client** using the Keyple middleware: contactless cards (Android NFC reader, or the reader of the Bluebird
  terminals) and SIM cards (OMAPI reader, work in progress);
- **Kotlin Multiplatform client** (Android, iOS, desktop) using the Keyple Interop libraries and the Server JSON API;
- **.NET client** (C#), showing how an application can interact with the server without using the Keyple middleware.

## Keyple Demos

This demo is part of the Keyple Demo Ticketing ecosystem, described in the [main README](../../README.md) with the
validation and inspection demos, and uses the [common library](../common/README.md) defining the data structures of
the card.

## Code Organization

This demo is organized in four source code folders, each one containing a `README` file giving more information:

- **server**: source code of the server part of the demo. The server should run on a computer with a JVM and have a card
  reader with a SAM connected.
- **client/interop-mobile-multiplatform**: source code of interop client part of the demo as a Kotlin Multiplatform
  project.
- **client/keyple-mobile-android**: source code of the client part of the demo as an Android project.
- **client/pc-dotnet**: source code of the client part of the demo not using the Keyple middleware as Microsoft Visual
  Studio project.

## Card Personalization and Contract Loading Procedures

### Card Personalization Use Case

This use case prepares the cards to be used for the following use cases by setting the appropriate values for the data
model fields of the Environment Record and making sure that the other relevant files are set to 0s (i.e. Events, 
Contracts and Counters).

Steps:
1. Detection and Selection
2. Clear the application

### Card Personalization Process

For this demo, a simple example card personalization procedure has been implemented. The steps below are those of the
Calypso cards: on the storage cards, the environment is written and the event and the contract are cleared directly,
without secure session (after the authentication of the sector for the MIFARE Classic cards).

Opening a Calypso secure session is mandatory for this procedure since we need to write on the card.

This procedure's main steps are as follows:
- Detection and Selection  
  - Detection Analysis:
    - Perform the Application Selection using the AID defined for the demo cards
    - If AID not found reject the card
    - If the status of the DF is invalid reject the card. <Exit process>
  - Selection Analysis:
    - If File Structure is unknown reject the card. <Exit process>
- Clear the Application
  - Open a secure session with the PERSONALIZATION access level, without reading any information.
  - Fill the environment structure, pack it into a byte array and update the environment record:
    - `EnvVersionNumber` = 1
    - `EnvApplicationNumber` = GlobalNumber++ (number generated by the server, initialized with its start time in
      seconds)
    - `EnvIssuingDate` = Current Date converted to `DateCompact`
    - `EnvEndDate` = (1st day of the month of Current Date + 6 years) converted to DateCompact
    - `HolderCompany`, `HolderIdNumber` and `EnvPadding` all filled to 0.
  - Clear the first event (update with a byte array filled with 0s).
  - Clear all contracts (update with a byte array filled with 0s).
  - Clear the counter file (update with a byte array filled with 0s).
  - Close the session.
  - Return the status of the operation to the upper layer. <Exit process>

### Contract Loading Use Case

This use case loads a new contract, or adds trips to or renews an existing contract of the same type, while updating the
contract priority levels if necessary.

Contracts can be period duration in which they are valid for a specific period or have an associated counter that
represents the number of trips left.

The data model also provides a traceability mode (authenticator added at the end of the contract, checked during the
Contract Analysis phase with the PSO commands of the SAM): it is not implemented by the demo, whose contracts have no
authenticator.

Contracts will be loaded first into blank records and then, when the card has no contract of the same type, the expired
contract with the lowest index will be replaced.

Steps:
1. Detection and Selection
2. Contract Analysis
3. Write the new contract, or update the existing one
4. Update contract priority value (if necessary)

### Contract Loading Process

For this demo, a simple example contract loading procedure has been implemented. The steps below are those of the
Calypso cards: on the storage cards, which have a single contract (its counter being in the contract record), the same
rules apply, the records being read and written directly, without secure session.

Opening a Calypso secure session is mandatory for this procedure since we need to write on the card.

This procedure's main steps are as follows:
- Detection and Selection
  - Detection Analysis:
    - If AID not found reject the card. <Exit process>
  - Selection Analysis:
    - If File Structure is unknown reject the card. <Exit process>
- Environment Analysis:
  - Open a secure session with the LOAD access level, reading the environment record.
  - Unpack environment structure from the binary present in the environment record.
    - If `EnvVersionNumber` of the Environment structure is not the expected one (==1 for the current version) reject
      the card. <Abort Transaction and exit process>
    - If `EnvEndDate` points to a date in the past reject the card. <Abort Transaction and exit process>
- Event Analysis:
  - Read and unpack the last event record. 
    - If `EventVersionNumber` is not the expected one (==0 for clean card or ==1 for the current version) reject the
      card. <Abort Transaction and exit process>
  - Store the `ContractPriority` fields in a persistent object with a flag to control any priority change set to false.
- Contract Analysis:
  - For each contract:
    - Read and unpack the contract record for the index being iterated.
      - If `ContractVersionNumber` is 0 ensure that the associated `ContractPriority` field value is 0 and move on to
        the next contract.
      - If `ContractValidityEndDate` points to a date in the past update the associated `ContractPriority` field present
        in the persistent object to 31 and set the change flag to true.
    - Add the contract to the list of the contracts of the card.
    - Return the list with the contract information. <Exit process>

-----------------

**Wait for input from the user regarding choice of product to load**

-----------------

- Write the new contract or update the existing one, and update the Contract Priority Value:
  - Fill the contract structure to update:
    - `ContractVersionNumber` = 1.
    - `ContractTariff` = Value provided by upper layer.
    - `ContractSaleDate` = Current Date converted to `DateCompact`.
    - If the operation renews a season pass (`ContractTariff` == 1) and the original `ContractValidityEndDate` is not in
      the past, set `ContractValidityEndDate` = original `ContractValidityEndDate` + 30
    - Else `ContractValidityEndDate` = (`ContractSaleDate` + 30 if `ContractTariff` == 1) or (`EnvEndDate` if
      `ContractTariff` == 2)
  - Pack the Contract structure to write into the contract record.
  - If the card already has a contract of the same type, use the index of this contract to update the information.
  - `ContractPriority` Analysis: 
    - If `ContractPriority` Value == `ContractTariff` skip the next points and go to CNT_UPD. (can be expired)
    - Else, Set `ContractPriority` Value = `ContractTariff`, set the flag to `true`.
  - If the operation is a new contract write (indicated by the layer above or when `ContractPriority` Value !=
    `ContractTariff`):
    - If there is one, or more, `ContractPriority` Field at 0 then the one with the lowest index will be the position of
      the contract to load. Set `ContractPriority` Value = `ContractTariff`, set the flag to true and go to CNT_UPD.
    - Else, if there is no `ContractPriority` Field at 0 then search for the first `ContractPriority` field at 31 and
      set that index as the one to load. Set `ContractPriority` Value = `ContractTariff`, set the flag to true and go to
      CNT_UPD.
    - Else (there are no expired nor empty positions) reject the card. <Abort Transaction and exit process>.
    - On a single contract card (Calypso Basic, storage cards), the contract of another type is replaced only if it is
      empty, expired or exhausted (multi-trip ticket without trips left); otherwise reject the card. <Abort Transaction
      and exit process>
  - CNT_UPD: Update the contract record present in the appropriate index with the binary data.
  - If the `ContractTariff` == 2 then increment the counter with the value sent from the upper layer (positive number of
    trips, the counter being limited to 16,777,215: 24 bits).
  - If `ContractPriority` changed flag is true, fill the event structure to update:
   - `EventVersionNumber` = 1.
   - `EventDateStamp` = value read from previous event.
   - `EventTimeStamp` = value read from previous event.
   - `EventLocation` = value read from previous event.
   - `EventContractUsed` = value read from previous event.
   - `ContractPriority1` = Value of index 0 of `ContractPriority` persistent object.
   - `ContractPriority2` = Value of index 1 of `ContractPriority` persistent object.
   - `ContractPriority3` = Value of index 2 of `ContractPriority` persistent object.
   - `ContractPriority4` = Value of index 3 of `ContractPriority` persistent object.
   - `EventPadding` = 0.
  - Pack the Event structure and update the last event with that binary data.
  - Close the session.
  - Return the status of the operation to the upper layer. <Exit process>
